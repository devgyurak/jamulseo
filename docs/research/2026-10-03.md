**빌드 컨테이너** — 공식 rust 이미지에는 Ubuntu 기반이 없다 (bookworm glibc 2.36 ≠ noble 2.39). 운영환경과 같은 glibc 로 빌드하려면:
- `FROM ubuntu:24.04@sha256:a853f94d226358a79c740cfc7bce0c289748f3fe3488d921d038ccd752c61b60` (2026-10-03 기준 인덱스 다이제스트)
- rustup-init 1.29.1 (`https://static.rust-lang.org/rustup/archive/1.29.1/x86_64-unknown-linux-gnu/rustup-init`, sha256 `dda7234360b7f578ca8b0ddcb80145646fa61a67c1720a5abc7051b35c9fcb71`) 로 `--default-toolchain 1.99.0 --profile minimal`
- 다이제스트는 보안 패치가 자동으로 들어오지 않으므로 갱신 절차를 둔다 (M4)

**상수 시간 하네스**
- Ubuntu 24.04 Valgrind 3.22.0. ctgrind 방식(`VALGRIND_MAKE_MEM_UNDEFINED`)은 libsecp256k1·BoringSSL 선례가 있다
- Rust 에서는 `crabgrind` 0.4.0 (no_std, bindgen 빌드 의존) — **2026-10-01 하루에 세 판이 나와 불안정**, 쓴다면 `=0.4.0` 고정. 대안: `jamulsoe-ct` 에 C shim 으로 `<valgrind/memcheck.h>` 매크로를 감싼다 (경계 밖이라 어느 쪽도 허용)
- dudect 기준 장비: ASLR 끄기, governor `performance`, 코어 격리, SMT 형제 offline, 터보 끄기(`intel_pstate/no_turbo=1`, AMD `cpufreq/boost=0`) — LLVM 벤치마킹 가이드 (https://llvm.org/docs/Benchmarking.html). 부스트를 끄면 Hertzbleed 류 DVFS 누출도 줄어든다. dudect 논문 기준 t 절댓값 4.5 (우리 `DUDECT_T_MAX` 와 같다)

## 4. GitHub 보호 설정

### 4.1 반드시 할 것 — `pull_request_target` 허용 (**2026-11-02 전**)

공개 저장소에서 `pull_request_target` 을 막는 기본 정책이 **2026-11-02 부터 강제**된다
(https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).
보호 경로 판정(`protected.yml`)이 이 이벤트로 돌므로, Settings → Actions → General 에서 이 이벤트를 허용하는 정책을 둬야 한다.
허용하지 않으면 그 체크를 필수로 건 PR 이 머지되지 못한다.

### 4.2 규칙셋 — `.github/rulesets/` (적용: `./.github/rulesets/apply.sh --apply`)

- 공개 저장소는 GitHub Free 에서도 규칙셋을 쓸 수 있다 [직접]
- 필수 체크의 이름은 워크플로 job 의 `name:` 이다: `보호 경로·DCO·승인 서명`, `게이트 (검증 대상 환경)`. `pull_request_target` 체크도 필수 체크로 인정된다 [직접]
- `allowed_merge_methods: ["merge"]` 로 머지 커밋만 허용, `strict_required_status_checks_policy` = 머지 전 최신화 [직접]
- **코드 오너 리뷰는 걸지 않는다.** 작성자는 자기 PR 을 승인할 수 없으므로 혼자 운영하면 머지가 불가능해진다 [직접 조합]. 승인의 증거는 리뷰가 아니라 **승인자 서명**이다 (`.agents/APPROVAL.md`)
- **"서명 필수"는 PR 의 모든 커밋에 적용된다** — 에이전트 커밋도 서명이 필요하다 → §4.3 의 두 키 구성
- GitHub 웹 머지 커밋은 GitHub 이 서명한다 [직접]
- **순서**: 원격이 비어 있으므로(2026-10-03 확인) **서명된 첫 커밋을 push 한 뒤** 적용한다. 먼저 걸면 "PR 필수" 때문에 첫 push 가 막힌다
- `integration_id: 15368`(GitHub Actions 앱)은 "앱이 최근 체크를 제출했어야 한다"는 조건이 있어, 워크플로가 한 번 돌기 전에는 거부될 수 있다

### 4.3 서명 키 — 두 개로 나눈다

| 키 | 용도 | 어디에 등록 | 에이전트가 쓸 수 있나 |
|---|---|---|---|
| **일상 서명 키** (소프트웨어 ed25519) | 모든 커밋 서명 ("서명 필수" 충족) | GitHub Signing Key | 예 — 그래서 승인 증거가 아니다 |
| **승인 키** (하드웨어 `ed25519-sk`) | 보호 경로 변경 커밋 (`Approved-by:`) | GitHub Signing Key **+ `.github/allowed_signers`** | 아니오 — 서명마다 터치 |

`check-protected-diff.sh` 는 서명자(`%GS`)가 `allowed_signers` 의 승인자 이메일과 같은지 본다. 일상 키는 `allowed_signers` 에 없으므로
서명이 유효해도 승인으로 인정되지 않는다. (git 소스 기준, `allowed_signers` 에 없는 키도 `%G?` 는 `G` 가 나오고 `%GS` 가 비므로
`%G?` 만 보면 안 된다 — 현재 스크립트는 둘 다 본다.)

macOS 에서 하드웨어 키 만들기 (이 Mac 의 `/usr/bin/ssh-keygen` 은 sk 키를 만들지 못함을 확인 — "No FIDO SecurityKeyProvider specified"):
```bash
brew install openssh                       # libfido2 포함. 설치하면 Apple 키체인의 암호 연동을 못 쓴다 (GitHub 문서 경고)
$(brew --prefix)/bin/ssh-keygen -t ed25519-sk -C dev@devgyurak.com -f ~/.ssh/jamulsoe_approve_sk   # 키가 Ed25519 미지원이면 ecdsa-sk
gh ssh-key add ~/.ssh/jamulsoe_approve_sk.pub --type signing --title "jamulsoe approval (sk)"
echo "dev@devgyurak.com namespaces=\"git\" $(cut -d' ' -f1,2 ~/.ssh/jamulsoe_approve_sk.pub)" >> .github/allowed_signers
```
- GitHub 에서 Verified 로 보이려면 **committer 이메일이 계정의 확인된 이메일**이어야 한다 → dev@devgyurak.com 을 devgyurak 계정에서 확인
- 이 저장소의 커밋 작성자는 `devgyurak <dev@devgyurak.com>` 으로 설정했다 (`git config --local`)

### 4.4 `refs/pull/N/merge` 를 쓰지 않는 이유

GitHub 문서: merge ref 는 "becomes outdated without warning" — PR 을 조회하기 전까지 다시 계산되지 않는다 [직접].
그래서 `protected.yml` 은 CI 안에서 `git merge-tree --write-tree base head` + `git commit-tree` 로 머지 결과를 **직접 계산**한다
(git 객체 연산 — PR 코드를 실행하지 않는다, 충돌이면 실패).
