# jamulsoe 구현 계획서

Oct 2, 2026 · @leegyurak

이 계획서는 외부 리뷰 네 차례를 반영해 2026년 10월 2일 기준으로 동결한다. 이후 변경은 G1(경계·API 동결)에서 시험기관 답변과 함께 반영한다.

## 개요

jamulsoe는 Rust로 구현하고 C ABI로 제공하는 오픈소스 국산 암호 모듈이다. 1차 목표는 ARIA-GCM, SHA-256, HMAC 범위로 KCMVP 보안등급 1 검증을 받는 것이다.

**목표**

- 상수 시간(constant-time)으로 구현한 ARIA를 검증 가능한 품질의 공개 소스로 제공
- C ABI(`libjamulsoe.so` + `jamulsoe.h`)로 C/C++, Java, Python, Go 등에서 바로 사용
- KS X ISO/IEC 19790 소프트웨어 모듈 요건을 처음부터 설계에 반영
- 재현 가능한 빌드로 검증필 공식 바이너리가 공개 소스에서 나왔음을 누구나 확인할 수 있게 함

**1차 검증 범위 (v1)**

| 구분 | 대상 | 비고 |
| --- | --- | --- |
| 블록암호 | ARIA-128/192/256 | KS X 1213-1, RFC 5794 |
| 운영모드 | GCM | AEAD, IV 96비트·태그 128비트 고정 |
| 해시 | SHA-256 | 무결성 시험에도 사용 |
| 메시지 인증 | HMAC-SHA-256 | 무결성 시험의 MAC |
| 운영환경 | Ubuntu 24.04 LTS, x86\_64 | 1개로 시작 |

**비목표 (v1)**: 난수발생기(DRBG)와 잡음원, 공개키·전자서명, TLS 프로토콜, 하드웨어 가속 경로, Windows/macOS. 모두 검증 범위를 키우므로 v1 이후로 미룬다.

## 저장소·크레이트 구조

검증 대상 바이너리는 `libjamulsoe.so`이고, 그 안을 세 크레이트로 나눠 unsafe 코드와 상태 관리를 알고리즘에서 분리한다. 무결성 태그 파일(`.hmac`)을 모듈 경계에 포함할지는 시험기관 답변 전까지 확정하지 않는다.

애플리케이션은 C ABI만 호출하고, 상태 검사와 자가시험은 module, 알고리즘은 core가 맡는다. 테스트, 퍼징, 바인딩 예제, 무결성 도구는 모두 경계 밖에 둔다.

```text

├─ crates/
│  ├─ jamulsoe-core/     # no_std 알고리즘: ARIA, GCM, SHA-256, HMAC
│  ├─ jamulsoe-module/   # 상태머신, 자가시험, 무결성 시험, CSP 제로화
│  └─ jamulsoe-ffi/      # C ABI (cdylib만), cbindgen 설정
├─ include/jamulsoe.h    # 생성된 헤더 (커밋해 ABI 변경 추적)
├─ exports.txt           # 허용 export 심볼 목록 (CI 비교 기준)
├─ tools/integrity/      # 빌드 후 무결성 태그 생성
├─ tests/vectors/        # KISA·RFC·NIST 테스트 벡터
├─ tests/negative/       # 실패 케이스 회귀 코퍼스
├─ fuzz/                 # cargo-fuzz 타깃
├─ bindings/             # Python·Java·Go 예제 (경계 밖)
├─ docs/kcmvp/           # 설계서·보안정책문서·CSP 인벤토리·형상관리문서 초안
├─ docs/provenance.md    # 참고 자료 출처·라이선스·차용 여부
└─ rust-toolchain.toml   # 툴체인 고정 (기준선 일부)
```

## 알고리즘 구현 계획

모든 알고리즘은 외부 의존성 없는 `#![no_std]` 순수 Rust로, 알고리즘당 구현 경로를 하나만 둔다. 모듈 경계 안의 코드는 전부 소스로 제출하므로, 경로가 하나여야 시험 범위가 작아진다.

### 상수 시간의 정의

이 문서에서 상수 시간은 "검증 대상 CPU와 고정된 컴파일러에서, 비밀값에 따라 제어 흐름과 메모리 접근 주소가 달라지지 않고, 비밀값에 의존하는 가변 지연 명령을 쓰지 않는 것"을 뜻한다. 상수 시간 GHASH는 x86\_64의 64비트 정수 곱셈이 입력과 무관하게 같은 시간에 끝난다는 가정에 기대므로, 이 가정도 보안정책문서에 명시한다. dudect·ctgrind 같은 도구는 증명이 아니라 회귀 탐지 수단이고, 어셈블리 감사를 함께 한다.

### ARIA

- **구조**: 128비트 블록, SPN, 라운드 수 12/14/16. 홀수·짝수 라운드가 S1, S2, S1⁻¹, S2⁻¹을 서로 다른 배치로 쓰므로, 암호화 방향만 쓰는 GCM에서도 S-box 4종이 모두 필요하다.
- **상수 시간 S-box**: 테이블 조회는 캐시 타이밍으로 키가 새므로 쓰지 않는다. S1은 AES S-box와 같아 공개된 비트슬라이스 회로를 참고할 수 있고, S2도 GF(2⁸) 역원 기반 아핀 변환이라 같은 역원 회로를 공유하도록 설계한다.
- **병렬 처리**: 4블록 단위 비트슬라이스로 CTR/GCM 처리량을 확보하고, 단일 블록도 같은 코어를 거친다.
- **확산층**: 16×16 이진 행렬(자기역행렬)이라 바이트 XOR만으로 구현되고, 원래 상수 시간이다.
- **키 스케줄**: CK1\~CK3 상수를 쓴 3단 Feistel로 W0\~W3를 만들고 회전·XOR로 라운드 키를 만든다. 복호 키는 확산층으로 유도한다.
- **노출 범위**: 블록 암·복호화는 모두 구현하되, 승인 서비스로는 GCM만 노출한다. 원시 블록 연산은 구현적합성 시험 하네스에서만 쓴다.

### GCM

- **기준 문서**: ARIA-GCM은 KCMVP 검증대상 알고리즘으로 이미 지정돼 있다. 목록이 제시하는 국내 참조 표준(KS X 1213-1, KS X 3254, KS X 3275, KS X ISO/IEC 10116, KS X ISO/IEC 19772)과 GVI Part 2를 1차 기준으로 구현하고, NIST SP 800-38D는 동작과 보안 제약을 확인하는 보조 참고자료로 쓴다. 표준 번호는 KISA 검증대상 알고리즘 페이지 기준이며, 원문을 확보하면 판·연도와 ARIA 운영모드 표준 KS X 1213-2의 해당 여부를 다시 확인한다.
- **파라미터 고정**: 공개 API는 96비트 IV와 128비트 태그만 지원한다. 다른 길이는 API에 존재하지 않아 오용과 시험 경우의 수가 함께 줄고, 96비트 IV는 IV를 GHASH로 처리하는 경로도 없앤다.
- **길이 상한**: 평문은 SP 800-38D 기준 2^39 − 256비트, 즉 2^36 − 32바이트(약 64GiB)가 한도이고 AAD에도 상한이 있다. 64비트 환경의 `size_t`는 이를 넘을 수 있으므로, GVI 허용값과 비교해 더 좁은 쪽을 상수로 정하고 진입점에서 검사한다.
- **GHASH**: 4·8비트 테이블 방식은 키 의존 메모리 조회라 배제한다. 정수 곱셈으로 만드는 상수 시간 캐리리스 곱셈(BearSSL `ghash_ctmul64` 방식)으로 구현한다.
- **검증 후 복호화**: open은 암호문과 AAD로 태그를 먼저 계산해 상수 시간으로 비교하고, 통과할 때만 CTR 복호화를 수행한다. 실패 시 출력에는 아무것도 쓰지 않는다. v1은 원샷 API만 제공하므로 이 구조에 제약이 없다.
- **IV 유일성**: v1은 DRBG가 없어 IV를 호출자가 주입한다. 사용자 안내서에는 SP 800-38D의 결정적 구성(고정 필드 + 호출 카운터)을 권장 규칙으로 제시하고, 키당 최대 호출 횟수와 같은 키·IV 재사용 금지를 명시한다.

### SHA-256

- KCMVP 목록의 참조 표준(KS X ISO/IEC 10118-3, KISA 페이지 기준)이 1차 기준이고 FIPS 180-4는 보조 참고다. 데이터 의존 분기·조회가 없는 비트 연산이라 상수 시간 부담이 적다.
- 스트리밍(init/update/final)과 원샷 API를 모두 제공한다.
- 확장: SHA-224는 SHA-256 코어(32비트 워드, 512비트 블록)를 재사용한다. SHA-384/512는 64비트 워드·1024비트 블록을 쓰는 SHA-512 코어를 별도로 추가한다.

### HMAC-SHA-256

- KCMVP 목록의 참조 표준(KS X ISO/IEC 9797-2, TTAK.KO-12.0330-Part1·Part2, KISA 페이지 기준)이 1차 기준이고 RFC 2104·FIPS 198-1은 보조 참고다. 키 길이 하한은 KCMVP의 보안강도 기준을 따르며, 정확한 값은 GVI에서 확인한다.
- 모듈 무결성 시험의 MAC으로도 쓰이므로 자가시험 KAT 대상이다.

### 이후 확장 (v2 이후)

| 알고리즘 | 용도 | 선행 조건 |
| --- | --- | --- |
| LEA | 고속·경량 블록암호 | ARIA 모듈 구조 재사용 |
| LSH-256/512 | 국산 해시 | 없음 |
| SHA-224 | 해시 확장 | SHA-256 코어 재사용 |
| SHA-384/512 | 해시 확장 | SHA-512 코어 별도 구현 |
| CTR\_DRBG (ARIA 기반) | 키·IV 생성 | 잡음원 설계 + 엔트로피 평가 |
| KBKDF, PBKDF2 | 키 유도 | HMAC |
| CBC, CTR 모드 | 레거시 연동 | 없음 |
| AES-NI/GFNI 가속 | 성능 | 검증 범위에 넣을지 별도 판단 |

## C ABI 설계

C ABI는 `jms_` 접두사를 쓰는 작은 함수 집합이고, 암호·상태 변경 함수는 모두 상태 코드(`int`)를 돌려준다. 조회 전용인 jms\_version만 정적 문자열 포인터를 돌려주며, 어떤 함수도 패닉을 밖으로 내보내지 않는다. 헤더는 cbindgen으로 생성하고 생성 결과를 저장소에 커밋해 ABI 변경을 diff로 추적한다.

### API 초안 (v0)

```c
/* 모듈 */
int         jms_init(void);       /* 미초기화: 자가시험 후 전이 / 승인 동작: JMS_OK(멱등) / 오류: JMS_ERR_STATE */
int         jms_status(void);     /* JMS_STATE_*, 모든 상태에서 호출 가능, 잠금 없이 atomic 조회 */
int         jms_selftest(void);   /* 승인 동작 상태에서만 허용, 수행 중 다른 암호 서비스는 대기 */
const char *jms_version(void);    /* 모든 상태에서 호출 가능 */

/* ARIA-GCM: IV 96비트, 태그 128비트 고정 */
/* JMS_GCM_MAX_TEXT_BYTES, JMS_GCM_MAX_AAD_BYTES: 헤더 상수, 값은 G1에서 확정 */
typedef struct { uint8_t b[12]; } jms_gcm_iv;
typedef struct { uint8_t b[16]; } jms_gcm_tag;
typedef struct jms_aead jms_aead;

int  jms_aria_gcm_new(jms_aead **out,     /* 진입 즉시 *out = NULL, 성공 시에만 핸들 기록 */
         const uint8_t *key, size_t key_len);
int  jms_aria_gcm_seal(jms_aead *ctx, const jms_gcm_iv *iv,
         const uint8_t *aad, size_t aad_len,
         const uint8_t *pt,  size_t pt_len,
         uint8_t *ct, size_t ct_cap,      /* ct_cap >= pt_len */
         jms_gcm_tag *tag);
int  jms_aria_gcm_open(jms_aead *ctx, const jms_gcm_iv *iv,
         const uint8_t *aad, size_t aad_len,
         const uint8_t *ct,  size_t ct_len,
         const jms_gcm_tag *tag,
         uint8_t *pt, size_t pt_cap);     /* 태그 검증을 통과한 때만 pt에 씀 */
int  jms_aead_zeroize(jms_aead *ctx);     /* 이후 seal/open은 JMS_ERR_CTX_STATE, 해제만 가능 */
void jms_aead_free(jms_aead *ctx);        /* 제로화 후 해제, NULL이면 아무 동작 없음 */

/* SHA-256 / HMAC-SHA-256: 출력 32바이트 고정 */
typedef struct { uint8_t b[32]; } jms_sha256_digest;
typedef struct { uint8_t b[32]; } jms_hmac_sha256_tag;
typedef struct jms_sha256_ctx jms_sha256_ctx;

int  jms_sha256(const uint8_t *msg, size_t len, jms_sha256_digest *out);
int  jms_sha256_new(jms_sha256_ctx **out);  /* 진입 즉시 *out = NULL, 성공 시에만 핸들 기록 */
int  jms_sha256_update(jms_sha256_ctx *ctx, const uint8_t *data, size_t len); /* 누적 길이 검사 */
int  jms_sha256_final(jms_sha256_ctx *ctx, jms_sha256_digest *out); /* 이후 update/final은 JMS_ERR_CTX_STATE */
void jms_sha256_free(jms_sha256_ctx *ctx);  /* NULL이면 아무 동작 없음 */
int  jms_hmac_sha256(const uint8_t *key, size_t key_len,
         const uint8_t *msg, size_t len, jms_hmac_sha256_tag *out);
```

### 오류 코드

| 코드 | 의미 |
| --- | --- |
| `JMS_OK` (0) | 성공 |
| `JMS_ERR_STATE` | 모듈 상태가 요청과 맞지 않음 (미초기화·오류 상태에서의 암호 서비스·`jms_selftest`, 오류 상태에서의 `jms_init`). 자가시험 중에는 이 오류 대신 대기 |
| `JMS_ERR_CTX_STATE` | 컨텍스트가 이미 제로화됐거나 final된 상태 |
| `JMS_ERR_PARAM` | NULL인 필수 포인터, 길이 > 0인데 NULL인 포인터, 허용되지 않는 키 길이, 최대·누적 길이 초과, 허용되지 않는 버퍼 겹침 |
| `JMS_ERR_BUFFER` | 출력 버퍼 용량 부족 |
| `JMS_ERR_AUTH` | GCM 태그 검증 실패 |
| `JMS_ERR_NOMEM` | 컨텍스트 메모리 할당 실패 |
| `JMS_ERR_SELFTEST` | 자가시험 실패, 모듈이 오류 상태로 전이됨 |
| `JMS_ERR_INTERNAL` | 예약 코드. v1에는 발생 경로가 없으며, 이후 버전에서 쓰면 치명적 오류로 모듈을 오류 상태로 전이시킴 |

v1에서 발생 가능한 모든 오류에서 출력 버퍼와 컨텍스트는 변경되지 않는다. 예외는 두 가지다. `JMS_ERR_SELFTEST`는 모듈을 오류 상태로 전이시키고, 생성 함수는 실패 시 `*out`을 NULL로 남긴다.

### 규칙

- **오류 시 무변경(공통 불변식)**: 모든 함수는 포인터, 길이, 상태, 겹침 등 실패할 수 있는 사전조건을 출력을 바꾸기 전에 검사한다. 예를 들어 `jms_sha256_final(ctx, NULL)`은 `JMS_ERR_PARAM`을 돌려주고 컨텍스트는 final되지 않은 채로 남는다.
- **내부 호출 경로(재진입 금지)**: 공개 `jms_*` 함수는 "lock 획득 → 모듈 상태 확인 → 내부 알고리즘 함수"로만 이뤄진 얇은 래퍼다. 자가시험과 무결성 시험은 공개 C ABI를 재진입하지 않고 내부 알고리즘 함수를 직접 호출한다. 자가시험은 write lock을 잡은 채 도므로 공개 API를 부르면 read lock에서 교착되고, `jms_init` 도중에는 아직 승인 동작 상태도 아니기 때문이다. 같은 내부 함수를 공유하므로 KAT는 실제 서비스가 사용하는 동일한 내부 암호 구현을 검사한다. C ABI 래퍼, 상태 검사, 잠금은 KAT 범위가 아니며 ABI·실패 케이스 테스트가 담당한다.
- **초기화 수명주기**: `jms_init`은 미초기화 상태에서 write lock을 잡고 자가시험을 거쳐 승인 동작 또는 오류 상태로 간다. 이미 승인 동작이면 `JMS_OK`(멱등), 오류 상태면 `JMS_ERR_STATE`다. 동시에 호출되면 나중 호출은 lock에서 대기했다가 먼저 끝난 결과에 위 규칙을 적용한다. `jms_selftest`는 승인 동작 상태에서만 허용한다.
- **지원하지 않는 선택지는 API에 없게**: IV, 태그, 다이제스트 길이를 인자로 받지 않고 고정 크기 구조체로 받는다. 캐스팅으로 잘못된 포인터를 넘기는 것까지 막지는 못하지만, 정상적인 호출에서 길이 선택지를 없앤다.
- **필수 포인터**: 길이 인자가 없는 포인터(컨텍스트, IV, 태그, 다이제스트, `**out`)는 항상 NULL이 아니어야 하며, NULL이면 `JMS_ERR_PARAM`이다. 생성 함수는 진입 즉시 `*out = NULL`로 두고, 객체를 완전히 초기화한 경우에만 핸들을 기록한다. `*_free(NULL)`은 아무 동작도 하지 않고, 이중 해제와 해제된 핸들 사용은 호출자 계약 위반으로 명시한다.
- **(포인터, 길이) 쌍**: 길이가 0이면 NULL을 허용하고, 길이 > 0이면 NULL이 아니어야 한다(위반 시 `JMS_ERR_PARAM`). Rust의 `slice::from_raw_parts`는 길이가 0이어도 NULL을 받으면 UB이므로, NULL로부터 슬라이스를 만들지 않고 길이 0은 내부에서 빈 슬라이스로 처리한다.
- **포인터 유효성(호출자 계약)**: NULL이 아닌 포인터는 명시된 길이만큼 접근 가능한 유효한 메모리를 가리켜야 하고, 타입 포인터는 해당 타입의 정렬을 만족해야 한다. 모듈이 검사하는 것은 NULL, 길이, 산술 오버플로, 겹침, 컨텍스트 상태다. 댄글링 포인터, 접근 불가능한 주소, 실제와 다른 길이, 정렬되지 않은 포인터는 검사할 수 없으며 호출자 계약 위반이다.
- **길이 상한**: GCM 평문·암호문과 AAD는 진입 시 `JMS_GCM_MAX_TEXT_BYTES`, `JMS_GCM_MAX_AAD_BYTES`로 먼저 검사한다. SHA-256의 바이트 단위 최대 입력은 2^61 − 1바이트(2^64 − 1비트)이고, 컨텍스트는 누적 입력 길이를 `checked_add`로 관리해 이를 넘으면 `JMS_ERR_PARAM`을 돌려주고 컨텍스트는 바꾸지 않는다. HMAC 메시지 상한은 내부 해시 입력이 `(key ⊕ ipad) ‖ msg`이므로 SHA-256 상한보다 64바이트 작다. HMAC 키도 SHA-256 최대 입력 이하여야 하며, 64바이트를 넘는 키는 SHA-256으로 정규화한다. 길이×8, 블록 수, offset + len 계산은 모두 checked arithmetic으로 하고, 상수는 헤더에 노출해 바인딩도 같은 값을 쓴다.
- **출력 용량**: 가변 길이 출력은 `*_cap`을 함께 받는다. 용량이 부족하면 `JMS_ERR_BUFFER`를 돌려준다.
- **버퍼 겹침**: v1에서 허용하는 유일한 겹침은 GCM의 `pt == ct` 완전 일치다. 그 밖에 입력과 출력, 출력과 출력(예: `ct`와 `tag`) 사이의 부분·완전 겹침은 모두 `JMS_ERR_PARAM`으로 거부한다. 입력끼리의 겹침(예: `aad`와 `pt`)은 허용하되, 그 입력 영역이 동시에 출력 영역인 경우는 허용하지 않는다. 따라서 in-place GCM에서는 AAD, IV, 태그가 공유 `pt`/`ct` 버퍼와 겹치면 안 된다. in-place는 `&mut [u8]` 하나로 처리하는 별도 경로로 나눠 aliasing UB를 피한다.
- **GCM open**: 암호문으로 태그를 먼저 검증하고 통과할 때만 복호화한다. 실패 시 출력에 쓴 것이 없으므로, in-place에서도 암호문이 그대로 남는다.
- **컨텍스트 상태**: `jms_aead`는 사용 가능 → 제로화됨, `jms_sha256_ctx`는 사용 가능 → final됨의 내부 상태를 갖는다. 제로화·final 이후의 호출은 `JMS_ERR_CTX_STATE`를 돌려주고, 해제만 가능하다.
- **메모리 할당**: 컨텍스트는 크기가 고정된 구조체 두 종류뿐이다. FFI 크레이트는 `Box::new` 대신 `std::alloc::alloc`으로 할당하고, 검증 대상 환경의 이 명시적 할당 경로에서 돌아온 NULL을 `JMS_ERR_NOMEM`으로 변환한다. 이는 jamulsoe가 수행하는 컨텍스트 할당의 실패 계약일 뿐, allocator가 스스로 abort하거나 OS의 OOM killer가 프로세스를 종료하는 경우까지 막는다는 약속은 아니다. AEAD 컨텍스트는 메모리를 먼저 확보한 뒤 키 스케줄을 계산해, 할당이 실패하면 비밀 중간값이 아예 만들어지지 않게 한다. `jamulsoe-core`는 힙을 쓰지 않는다.
- **모듈 상태별 허용 서비스**: 암호 서비스는 승인 동작 상태에서만 동작한다. 상태 조회, 버전 조회, 제로화, 해제는 오류 상태를 포함한 모든 상태에서 허용한다.
- **자가시험과 스레드**: 상태 표시용 atomic과 서비스 직렬화용 RwLock을 분리한다. 암호 서비스는 반드시 "read lock 획득 → 상태 확인 → 연산" 순서를 지킨다. 순서를 바꾸면 자가시험이 실패한 직후에도 연산이 나갈 수 있다. `jms_init`과 `jms_selftest`는 write lock을 잡고, 그동안 들어온 호출은 대기했다가 승인 동작이면 실행, 오류 상태면 `JMS_ERR_STATE`를 돌려준다. `jms_status`는 잠금 없이 atomic만 읽어 자가시험 중에도 즉시 응답한다. 하나의 컨텍스트는 한 스레드에서만 쓴다.
- **패닉**: 릴리스 프로파일은 `panic = "abort"`. FFI 함수는 산술·길이를 모두 검사해 오류 코드로 돌려주고, 패닉 경로를 만들지 않는다.
- **제로화**: 컨텍스트 단위다. `jms_aead_zeroize`와 `*_free`가 키를 지운다. 모듈 전체 제로화는 두지 않고, 시험기관이 요구하면 컨텍스트 레지스트리를 추가한다.
- **unsafe 경계**: `jamulsoe-core`는 `#![forbid(unsafe_code)]`. 원시 포인터와 할당을 다루는 unsafe는 FFI 크레이트에만 둔다.
- **export 허용 목록**: `exports.txt`에 공개 심볼을 고정하고, CI가 `nm -D --defined-only` 결과와 비교해 심볼이 하나라도 늘면 실패시킨다.
- **산출물**: 검증 릴리스는 `cdylib`(`.so`)만 만든다. staticlib은 검증 대상이 아니므로 검증 릴리스에서 제외한다.
- **바인딩**: Python(ctypes/cffi), Java(FFM API), Go(cgo) 예제는 모듈 경계 밖 디렉터리에 둔다.

### CSP 인벤토리

구현 전에 지워야 할 대상을 먼저 목록화한다. 원본 키뿐 아니라 키에서 파생된 값과 스택 위 임시값도 대상이다. GCM은 암호화 방향만 쓰므로 컨텍스트에는 복호 라운드 키를 두지 않는다.

| ID | 대상 | 생성 | 보관 | 파기 |
| --- | --- | --- | --- | --- |
| CSP-01 | ARIA 입력 키의 모듈 내 사본과 키 스케줄 중간값(W0\~W3) | `jms_aria_gcm_new` | 키 확장 중 스택 | 키 확장 직후 |
| CSP-02 | ARIA 암호화 라운드 키 | `jms_aria_gcm_new` | `jms_aead` 컨텍스트 | `jms_aead_zeroize`, `jms_aead_free` |
| CSP-03 | GHASH 키 H (= 영 블록의 암호문) | `jms_aria_gcm_new` | `jms_aead` 컨텍스트 | `jms_aead_zeroize`, `jms_aead_free` |
| CSP-04 | GCM 키스트림·카운터 임시값 | seal/open 호출 | 스택 | 함수 반환 전 |
| CSP-05 | HMAC 키, 64바이트 초과 키의 SHA-256 정규화 값, ipad/opad 파생 상태 | `jms_hmac_sha256` 호출 | 스택 | 함수 반환 전 |

무결성 시험용 고정 HMAC 키의 CSP 해당 여부와 관리 방식은 시험기관 확인 후 확정한다.

**제로화 구현**: 비밀값 타입은 `Copy`/`Clone`을 구현하지 않아 구조적으로 복제를 막는다. `Drop`과 함수 종료 지점에서 `write_volatile` + `compiler_fence`로 덮어쓰고, 최적화로 제거되지 않았는지 릴리스 빌드 어셈블리로 확인한다. 레지스터·컴파일러가 만든 스택 사본은 완전히 통제할 수 없다는 한계도 보안정책문서에 적는다.

**승인 모드만 제공**: 비승인 알고리즘을 모듈에 넣지 않아, 별도 "비승인 모드" 없이 검증대상 동작모드만 존재하게 한다. 모듈 상태 전이는 아래 그림으로 정리한다.

| 퍼징 | FFI 경계, GCM open | cargo-fuzz(libFuzzer), 차등 퍼징 포함 |
| 상수 시간 회귀 탐지 | S-box, GHASH, 태그 비교 | dudect 방식 통계 검사, Valgrind 비밀값 표시(ctgrind 방식), 릴리스 어셈블리 감사 |
| 메모리 안전 | FFI 크레이트 | Miri, C 테스트 하네스 + AddressSanitizer |
| 실패 주입(자가시험·할당) | KAT, 무결성 시험 | 테스트 전용 feature로 실패를 강제해 오류 상태 전이와 오류 상태의 허용 서비스 확인. 할당 실패 주입 시 JMS\_ERR\_NOMEM, \*out == NULL, CSP 잔존 없음, 모듈 상태 불변 확인 |
| ABI·심볼 회귀 | `jamulsoe.h`, `libjamulsoe.so` | cbindgen 결과 diff, `nm -D`를 `exports.txt`와 비교, C 예제 빌드·실행 |

- **자가시험 실패 주입**은 시험기관이 실제로 요구하는 항목이다. 주입 경로는 검증 바이너리에 들어가지 않도록 빌드 플래그로 분리하고, 시험용 빌드를 따로 제출할지는 시험기관과 협의한다.
- **상수 시간 검사**는 증명이 아니라 회귀 탐지다. 컴파일러 버전이 바뀔 때마다 다시 돌리고 비밀값 경로의 어셈블리를 다시 검토한다. Rust 컴파일러는 분기 없는 코드에 분기를 넣을 수 있어, 비밀값 연산에는 최적화 장벽(value barrier) 헬퍼를 쓴다.
- **실패 케이스 코퍼스**는 버그가 나올 때마다 재현 입력을 추가해 고정 회귀 테스트로 유지한다. FFI 암호 라이브러리는 정상 경로보다 이쪽에서 사고가 자주 난다.

## 빌드·배포·형상관리

재현 가능한 빌드의 목적은 검증필로 배포한 공식 바이너리가 공개된 특정 소스와 툴체인에서 재현됨을 제3자가 확인하게 하는 것이다. 사용자가 직접 빌드한 결과물에 검증효력을 주는 장치는 아니며, 검증효력은 모듈명·버전·운영환경·형상 기준으로 관리된다.

### 재현 가능한 빌드

- **툴체인 기준선**을 형상으로 고정한다: rustc(`rust-toolchain.toml`), `Cargo.lock`, 링커·binutils, glibc, target triple, 대상 CPU 기준선, LTO·codegen-units·strip 설정. 외부 크레이트 의존성은 0개를 유지한다.
- **대상 CPU**: `-C target-cpu=native`는 쓰지 않고, 검증 대상 CPU 기준선을 명시적으로 지정한다.
- 빌드는 다이제스트로 고정한 컨테이너 이미지에서 하고, `--remap-path-prefix`와 `SOURCE_DATE_EPOCH`로 경로·시각 차이를 없앤다.
- CI가 서로 다른 두 러너에서 빌드해 SHA-256이 같은지 매번 비교한다.

### 무결성 태그

- 빌드 후 도구(`tools/integrity`)가 `libjamulsoe.so`의 HMAC-SHA-256 태그를 만들고, `jms_init`이 로드 시 다시 계산해 비교한다. 일치하지 않으면 오류 상태로 간다.
- 태그를 별도 파일(`.hmac`)로 둘지 바이너리에 넣을지는 독자적으로 정하지 않고, GVI가 인정하는 패턴을 시험기관에 확인해 따른다. 그 전까지 모듈 경계도 확정하지 않는다.
- 전자서명 기반 검사는 공개키 검증 구현이 모듈에 들어와 범위가 커지므로 v1에서는 고려하지 않는다.
- 한계: 무결성 시험은 우발적 손상과 단순 변조를 감지할 뿐, 바이너리와 태그를 함께 바꿀 수 있는 공격자에 대한 신뢰 기준점은 아니다. 이 점을 보안정책문서에 명시한다.

### 브랜치·버전 정책

| 대상 | 정책 |
| --- | --- |
| `main` | 일반 개발. SemVer로 릴리스 |
| `kcmvp/v1` 브랜치 | 검증 제출 버전을 동결. 변경은 곧 재검증 사유이므로 수정하지 않음 |
| 태그 | 서명된 태그(`v1.0.0-kcmvp` 등). 릴리스에 `.so`, 무결성 태그, SHA-256 목록, SBOM, 툴체인 기준선 명세 첨부 |
| 보안 수정 | `main`에 반영하고, 심각도에 따라 재검증 신청 여부를 판단 |

### 기여·라이선스

- 라이선스는 Apache-2.0으로 한다.
- 기여에는 DCO(Signed-off-by)를 요구한다. 모든 변경의 작성자를 추적할 수 있어 형상관리문서의 근거가 된다.
- `main` 보호 규칙(리뷰 필수, 서명 커밋)과 2단계 인증을 켜 두어, 시험기관의 개발 환경 보안 점검에 대비한다.
- **코드 출처 기록**: KISA 참고용 소스코드, 비트슬라이스 S-box 회로, BearSSL GHASH 같은 외부 자료는 테스트 오라클과 설계 참고로만 쓰고 코드를 옮기지 않는다. 참고한 자료의 출처, 논문, 라이선스, 실제 차용 여부, 내려받은 자료의 SHA-256과 확보 날짜를 `docs/provenance.md`에 기록한다.

## 구현 체크리스트

계획서 계약을 코드로 옮길 때 지켜야 할 구현 규칙이다. 각 항목은 해당 코드가 들어가는 PR에서 테스트와 함께 체크한다.

**겹침 검사가 스스로 UB를 만들지 않게**

- [ ] FFI 진입 시 raw pointer의 주소값(`ptr.addr()`)과 길이로 `[start, end)`를 checked arithmetic으로 계산하고, `end`가 넘치면 `JMS_ERR_PARAM`을 돌려준다.
- [ ] 서로 다른 allocation일 수 있는 포인터에 `offset_from` 같은 포인터 산술을 쓰지 않는다. 주소는 정수로만 비교한다.
- [ ] 길이 0인 구간은 어떤 구간과도 겹치지 않는 것으로 처리한다.
- [ ] NULL·길이·상한·겹침 검사를 모두 통과한 뒤에만 Rust 참조와 슬라이스를 만든다. 슬라이스를 만든 뒤 겹침을 확인하지 않는다.

**할당·초기화·해제에서 CSP 사본을 만들지 않게**

- [ ] 스택에서 완성한 `jms_aead` 값을 `ptr::write`로 옮기지 않는다. 할당한 storage를 초기화한 뒤 라운드 키와 GHASH H를 최종 컨텍스트 위치에 직접 계산해 넣는다.
- [ ] 키 스케줄 함수는 배열을 값으로 돌려주지 않고 출력 대상(`&mut`)을 인자로 받는다. 값 반환은 사본을 만든다.
- [ ] 키 스케줄 중 스택에 남는 W0\~W3 등 중간값은 함수 반환 전에 제로화한다. 레지스터 spill까지는 통제할 수 없다는 한계는 보안정책문서의 기존 문구를 따른다.
- [ ] free 경로는 `zeroize → drop이 필요한 필드 처리 → 같은 Layout으로 dealloc` 순서를 지키고, 이 순서를 테스트로 고정한다.

**`JMS_ERR_INTERNAL`은 예약 코드로 둔다**

- [ ] v1에는 발생 경로를 두지 않는다. 입력·상태·할당·인증·자가시험 실패는 이미 전용 코드가 있고, 진짜 내부 불변식 파괴는 `panic = "abort"`로 프로세스가 종료된다.
- [ ] 코드 번호는 ABI 안정성을 위해 유지한다. 이후 버전에서 쓰게 되면 치명적 오류로 정의해 모듈을 오류 상태로 전이시킨다.

## 리스크와 열린 질문

가장 큰 리스크는 기술이 아니라 제도 해석이고, 아래 질문 대부분은 KISA·NSR 문의 답변과 KISA 심화 교육으로 풀린다. 답을 받기 전에는 M0\~M1만 진행하고, 모듈 경계와 공개 API는 G1에서 동결한다.

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 개인 명의 신청·계약 불가 | 검증 경로 자체가 막힘 | 개인사업자 설립, 또는 협력 회사가 신청기관이 되는 방식 |
| GCM IV를 모듈 내부에서 생성하라는 요구 | DRBG와 잡음원이 v1에 들어와 범위가 크게 늘어남 | GVI Part 1 확인 후 필요하면 CTR\_DRBG를 v1로 당김 |
| Rust 구현에 대한 시험기관 경험 부족 | 소스 검토 지연, 추가 설명 요구 | 설계서에 언어 특성(소유권, unsafe 경계) 설명 절을 추가 |
| Rust 표준 라이브러리가 바이너리에 정적 링크됨 | 모듈 경계에 std 코드가 포함된다고 볼 수 있음 | core는 `no_std`, FFI는 std 사용 범위를 최소화. 필요하면 `no_std` cdylib로 전환 |
| 검증 OS의 EOL | 검증효력 유지 불가 | 지원 기간이 긴 LTS를 고르고, EOL 6개월 전 재검증 신청 |
| 평일 업무시간 대응 | 시험 중 설명회·보완 요청 대응이 늦어짐 | 시험 기간에 연차 계획, 제출물 완성도를 높여 보완 횟수를 줄임 |
| 상수 시간 회귀 | 컴파일러 업데이트로 타이밍 누출 발생 | 툴체인 고정 + CI 상수 시간 검사 |

**시험기관에 확인할 질문**

- [ ] 개인(또는 개인사업자) 명의로 신청·계약이 가능한가
- [ ] 소스가 공개된 모듈도 접수되는가, 형상관리에서 유의할 점은
- [ ] Rust 구현과 표준 라이브러리 정적 링크를 어떻게 보는가
- [ ] DRBG 없이 키·IV를 외부에서 주입받는 GCM 구성이 허용되는가
- [ ] 96비트 IV·128비트 태그만 지원하는 구성으로 구현적합성 시험을 받을 수 있는가, GCM 최대 입력 길이의 허용값은
- [ ] 블록암호 구현적합성 시험에 ECB 등 원시 블록 연산 인터페이스가 필요한가
- [ ] 무결성 태그를 별도 파일로 둘지 바이너리에 넣을지, 태그 파일을 모듈 경계에 포함하는가
- [ ] 알고리즘 KAT를 init에서 수행할 때 분류를 조건부 자가시험으로 보는가(GVI Part 1 해석)
- [ ] 모듈 전체 제로화 서비스가 필요한가, 컨텍스트 단위 제로화로 충분한가. 특히 자가시험 실패로 오류 상태에 들어갈 때 이미 존재하는 AEAD 컨텍스트의 CSP를 즉시 제로화해야 하는가, 아니면 암호 서비스를 차단하고 호출자의 zeroize/free만 허용하면 되는가(전자면 컨텍스트 레지스트리가 필요해 구조가 바뀜)
- [ ] 무결성 시험용 고정 HMAC 키가 CSP에 해당하는가, 해당한다면 어떻게 관리해야 하는가
- [ ] 시험 수수료, 예상 대기·소요 기간
