**단계**: ⑤ REVIEW
**전제**: 🚫 구현한 에이전트와 다른 세션
**정의**: `docs/CONTRACTS.md#c1` — "검증 대상 CPU와 고정된 컴파일러에서, 비밀값에 따라 제어 흐름과 메모리 접근 주소가
달라지지 않고, 비밀값에 의존하는 가변 지연 명령을 쓰지 않는 것"

감사 절차:
1. **비밀값 흐름을 그린다** — 키, 라운드 키, H, 키스트림, 평문, 계산된 태그, HMAC 키·ipad/opad 상태가 어디로 흐르는가
2. **소스에서** 비밀값에 닿는 `if`/`match`/`while`/`?`/조기 `return`, 배열 인덱스, `/`·`%`, `==` 비교, `bool` 단락 평가(`&&`·`||`)를 찾는다
3. **어셈블리에서** 확인한다 — `./scripts/ct.sh --asm <함수 경로>` 로 릴리스 빌드(기준 CPU·기준 툴체인)의 비밀값 경로를 덤프하고,
   조건 분기(`jcc`), 비밀값 주소의 메모리 접근, `div`/`idiv`, 컴파일러가 만든 분기·`cmov` 대체 여부를 본다
4. **value barrier 가 실제로 장벽인가** — 최적화로 사라졌는지 어셈블리로 확인
5. **도구 결과를 해석한다** — `./scripts/ct.sh` 의 dudect t-값, ctgrind 보고. 통과는 "이 측정에서 못 찾았다"일 뿐이다
6. **제로화가 남아 있는가** — `write_volatile` 이 어셈블리에 남았는지 (C4 의 어셈블리 확인을 겸한다)

판정 기준:
- 비밀값 의존 분기·주소·가변 지연이 **어셈블리에 있으면 [P1]**. 실패 시나리오에는 비밀값·명령·관측 수단을 쓴다
- 소스는 깨끗한데 툴체인·플래그 변경으로 생긴 경우도 [P1] — 툴체인 기준선이 바뀌면 전부 다시 본다
- 64비트 곱셈 상수 시간 가정처럼 **가정에 기대는 곳**은 보안정책문서에 그 가정이 적혀 있는지 확인한다

권한과 한계:
- ❌ "dudect 가 통과했으니 괜찮다"로 끝내지 않는다. 도구는 회귀 탐지일 뿐이다
- ❌ 임계값(`DUDECT_T_MAX`)을 올리자고 제안하지 않는다
- ✅ 감사 결과를 **`docs/audits/<날짜>-<조항>-<주제>.md` 새 파일로 직접** 남긴다 (`docs/audits/README.md` 형식 — contract·toolchain·commit·scope·verdict).
  계약 레지스트리의 manual 단계(C1-09, C4-03 등)는 이 파일을 증거로 연결한다. 쓰기는 **이 디렉터리에만** 한다 — 코드는 고치지 않는다
- 마지막에 **"확인하지 못한 것"**(예: 검증 대상 CPU 실기 측정 없음, 레지스터 spill)을 반드시 쓴다
